## 端末ごとの鍵で暗号化する

シークレットは、承認済みの各端末が復号できるように暗号化します。
復号鍵と変更に署名する鍵は分離され、秘密鍵は端末で管理します。
変更を取得した端末は、署名、ダイジェスト、承認済みメンバーの情報を照合してからデータを採用します。

暗号化には age を使い、耐量子方式の ML-KEM-768 と、X25519 または P-256 を組み合わせます。
この **ハイブリッド暗号** は、一つの公開鍵暗号方式に保護を依存させないための設計です。

## 秘密鍵を保管する

利用できる場合、Windows と Linux では TPM 2.0 を、macOS では Secure Enclave を使います。
ハードウェアが利用できない場合は、Windows の Credential Manager、Linux の Secret Service、macOS の Keychain を利用できます。
ハードウェアと OS keyring の両方が利用できない場合、鍵を作成できません。
Linux で TPM が存在してもアクセス権が不足している場合は、自動で OS keyring に切り替わらずに停止します。

ハードウェアを使う場合、P-256 の秘密鍵はハードウェア内で使います。
ML-KEM の鍵の元になる seed は、その P-256 鍵に結び付けて端末上で暗号化し、ML-KEM の処理はホスト側で実行します。
このため、将来の量子攻撃を評価する際は、保存先の暗号文に加え、端末にある暗号化済みの seed が流出する可能性も考慮します。
OS や enbu のプロセスが侵害されると、正規の鍵操作を悪用してシークレットを取得されるおそれがあります。
管理者の鍵が侵害された場合は、攻撃者が新しい端末を承認できる可能性もあります。

| プラットフォーム | 優先する保管方法 | ハードウェアが利用できない場合 |
| --- | --- | --- |
| Windows | TPM 2.0 | Credential Manager |
| macOS | Secure Enclave | Keychain |
| Linux | TPM 2.0 | Secret Service |

## 初回の設定を信頼する

`enbu.toml` には、メンバーと権限を管理する署名付き履歴の起点が記録されています。
これを **Control genesis** と呼びます。
初回に受け取った設定を起点に以降の履歴を検証するため、`enbu.toml` は信頼できる共有経路から受け取ってください。

端末が記録済みの起点と異なる設定を見つけると、`trust_root_changed` として操作を停止します。
意図したワークスペースの再作成かどうかを管理者に別の経路で確認してから、新しい起点を受け入れてください。

## FAQ

### ストレージ管理者はシークレットを復号できますか？

復号には承認済みの端末の鍵が必要です。
ストレージ管理者には暗号文やメタデータを閲覧する権限があり、データの削除や配信の妨害も可能です。

### 保存先が古い状態を返したら検出できますか？

端末は、過去に受け入れた状態を記録し、既知の状態が見えなくなったことを検出します。
初めて接続する端末や、最新の変更をまだ見ていない端末は、隠された変更を見つけられない場合があります。

### セキュリティの検証には何を使っていますか？

リポジトリでは、ユニットテスト、E2E テスト、決定的シミュレーション、実機でのハードウェアテストを公開しています。
公開資料からは独立した第三者監査の完了を確認できません。

### 問題が起きたときに何を確認できますか？

`enbu doctor` で、鍵の保管先、認証、ストレージの読み取り、署名付き履歴、暗号文の整合性や復号の可否を確認できます。
機械処理には `enbu doctor --json` を使えます。

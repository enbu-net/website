## 別の端末の変更を取り込む

`enbu pull` は、選択中の環境の変更を取得し、署名付き履歴を検証してからシークレットを復号します。
復号した値は、その環境に設定された出力ファイルに反映します。

## 同時編集の競合を解決する

enbu は、各変更を **リビジョン** として保存します。
複数人が同じリビジョンから別々のキーを変更した場合は、共通の祖先を使って両方の変更を統合します。
同じキーを別々の値に変更した場合は競合として報告し、どの値を採用するか利用者が決めます。

`enbu resolve` を実行すると、競合したキーの候補と、確認した競合を指定するための ID を表示します。
たとえば `API_KEY` の候補 1 を採用する場合、次の `CONFLICT_ID` を表示された ID に置き換えます。

```sh
enbu resolve --seen CONFLICT_ID --pick API_KEY=1
```

## 履歴を調べて復元する

`enbu history list` でリビジョンを一覧できます。
たとえば、リビジョン 3 と 5 の差分は `enbu history diff 3 5` で確認できます。
たとえばリビジョン 3 に戻すには、`enbu history restore 3` を実行します。
復元すると、選んだリビジョンの内容が現在の変更として新たに公開されます。

## FAQ

### 履歴はいつ削除されますか？

履歴は管理者が明示的に整理するまで残ります。
たとえば `enbu history compact --keep 50` で保持範囲を指定できます。
この操作には、S3 や GHCR など、削除に対応する保存先が必要です。

### 履歴が増えると毎回すべての暗号文を取得しますか？

取得する暗号文は操作に必要なものに絞られます。
履歴が長くなると、保存先でのリビジョンの列挙や、署名付き状態を検証する処理は増えます。

### 端末の時計がずれると、直前の変更を失いますか？

enbu は、変更の前後関係を署名付きリビジョンの親子関係から判断します。
競合の判定には、この親子関係と変更した値を使います。
